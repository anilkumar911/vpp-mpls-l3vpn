1. MPLS Service Chaining — Overview

In a standard MPLS L3VPN, traffic flows directly between Provider Edge (PE) routers. Each PE pushes a transport label (to reach the remote PE) and a VPN label (to identify the VRF at the remote PE), then forwards the packet through the core:

CE1 → PE1 (push labels) → LSR (swap) → PE2 (pop labels) → CE2

Service chaining inserts a security appliance (the CNHE datanode) into this MPLS forwarding path. The security device receives VPN traffic, sends it through a security service (firewall/IDS), and then re-injects it into the MPLS backbone with new labels targeting the correct destination PE.

The key principle: all VPN traffic for a given organization must pass through the security device — in both directions. The datanode sees traffic from CE1→CE2 and CE2→CE1, so security policy can be applied symmetrically.

2. How Service Chaining Works in This Lab

2.1 The Service-Chained Path

Instead of PE1 sending traffic directly to PE2 via LSR1→LSR2, traffic is diverted to the datanode for security inspection:

CE1 → PE1 → LSR1 → LSR2 → GRE → Datanode → Geneve → Frouter → Geneve → Datanode → GRE → LSR2 → PE2 → CE2

2.2 Forward Path (host1 → host2)

  1. PE1 receives the packet from CE1 and pushes MPLS labels [transport][VPN 18] toward PE2 (10.255.0.2) via LSR1.
  2. LSR1 → LSR2 swap transport labels through the backbone.
  3. LSR2 (configured as a GRE endpoint) receives the MPLS packet. Instead of forwarding directly to PE2, LSR2 encapsulates it in GRE and sends it to the datanode: GRE src=203.0.113.1 dst=203.0.113.2, carrying MPLS labels [310 neos][1100 eos].
  4. Datanode VPP decapsulates GRE, processes MPLS:
    • Label 310 (non-eos): transport deaggregation — look up the next label
    • Label 1100 (eos): disposition — strip MPLS and do an IPv4 lookup in org-pre-security-1000 VRF
  5. The pre-security VRF routes 10.1.2.0/24 via the CNHE Geneve tunnel (cnhe-gnv) to frouter (192.168.80.100). VPP encapsulates in Geneve with VNI 0xFFFFFF and CNHE TLV options.
  6. Frouter (reflect mode) receives on UDP/6081, inspects/reflects the packet back via Geneve with the original CNHE header preserved.
  7. Datanode receives the Geneve return. CNHE matches VNI 16777215, decapsulates, and delivers the inner packet to the post-security VRF (org-post-security-1000).
  8. The post-security VRF routes 10.1.2.0/24 via gre0 with MPLS out-labels [1500][500]. VPP pushes the labels, encapsulates in GRE, and sends to LSR2 (203.0.113.1).
  9. LSR2 decapsulates GRE, forwards the MPLS packet through the backbone to PE2, which dispositions it into VRF10 and delivers to CE2 → host2.

2.3 Return Path (host2 → host1)

The return path is symmetric — traffic from CE2 is also diverted to the datanode:

  1. PE2 pushes MPLS labels [transport][VPN 18] toward PE1 via LSR2→LSR1.
  2. LSR2 again encapsulates in GRE to the datanode with labels [310][1100].
  3. The datanode follows the same chain: MPLS disposition → pre-security → Geneve → frouter → Geneve return → post-security.
  4. The post-security VRF routes 10.1.1.0/24 via gre0 with out-labels [1400][600] (different label stack to reach PE1 side).
  5. Traffic flows via LSR2 → LSR1 → PE1 → CE1 → host1.

Key insight: Both directions (forward AND return) pass through the datanode. The datanode has separate MPLS label stacks for each direction in the post-security VRF: [1500][500] toward PE2/CE2, [1400][600] toward PE1/CE1. This ensures inspected traffic is re-injected into the correct direction of the MPLS backbone.

3. Route Reflector with Next-Hop Self

3.1 The Problem: Static Label Configuration

In this lab, service chaining is achieved with static MPLS labels and GRE routing on LSR2 and the datanode. LSR2 has static MPLS-over-GRE tunnels configured, and the datanode has manually-configured MPLS labels (310, 1100) and post-security out-labels (1400, 600, 1500, 500). This works for a lab but doesn't scale:

  • Every new VRF/customer requires new static label allocations on the datanode and LSR2
  • Route changes on the PEs require manual updates to the datanode's post-security label stacks
  • Adding new sites (CE3, CE4, ...) means more static entries

3.2 The Solution: Datanode as BGP Route Reflector

In a production deployment, the datanode should participate in MP-BGP as a route reflector (RR) for VPNv4 routes. Here's how it works:

               iBGP (RR client)                   iBGP (RR client)
       PE1 ───────────────── Datanode (RR) ────────────────── PE2
   AS 65000                 next-hop self                     AS 65000
   Loopback: 10.255.0.1     Loopback: 10.255.0.3              Loopback: 10.255.0.2
  1. PE1 advertises VPNv4 route RD:10.1.1.0/24 with VPN label 18 and next-hop 10.255.0.1 to the datanode (RR).
  2. PE2 advertises VPNv4 route RD:10.1.2.0/24 with VPN label 18 and next-hop 10.255.0.2 to the datanode (RR).
  3. The datanode (RR) re-advertises each route to the other PE, but with next-hop self:
    • To PE1: 10.1.2.0/24 next-hop 10.255.0.3 (datanode), VPN label 1100 (disposition into pre-security)
    • To PE2: 10.1.1.0/24 next-hop 10.255.0.3 (datanode), VPN label 1100
  4. Now PE1 thinks PE2's routes are reachable via the datanode. It pushes [transport-to-datanode][1100] — traffic naturally arrives at the datanode for inspection.
  5. After inspection, the datanode knows the original PE's next-hop and VPN label from the received BGP update. It pushes [transport-to-PE2][18] and forwards out the GRE/MPLS tunnel.

Why next-hop self? By changing the BGP next-hop to itself, the datanode forces PEs to send all VPN traffic through it. Without next-hop self, PEs would resolve the original PE's next-hop via IGP and send directly, bypassing the security device entirely.

3.4 Route Reflector Behavior

Standard BGP route reflectors reflect routes between clients without modifying next-hop. The datanode deviates from this by setting next-hop self on reflected routes. This is the critical mechanism:

# Standard RR (not service-chained):
PE1 advertises: 10.1.1.0/24 NH=10.255.0.1 label=18
RR reflects to PE2: 10.1.1.0/24 NH=10.255.0.1 label=18   (NH unchanged)
==> PE2 sends directly to PE1 (no security inspection)

# Datanode RR (service-chained):
PE1 advertises: 10.1.1.0/24 NH=10.255.0.1 label=18
RR reflects to PE2: 10.1.1.0/24 NH=10.255.0.3 label=1100 (NH = datanode, label = pre-sec)
==> PE2 sends to datanode --> inspection --> datanode forwards to PE1

The datanode stores the original route attributes (original NH, original label) so it can construct the correct label stack after inspection to forward traffic to the destination PE.

4. Split VRF Architecture in Datanode

4.1 What is a Split VRF?

The datanode maintains two separate VRFs per organization (per-tenant). This is the "split VRF" model — a single organization's routing table is split into a pre-security half and a post-security half:

VRFNameFIBTable IDPurpose
Pre-Securityorg-pre-security-1000fib 616778216Receives traffic before security inspection
Post-Securityorg-post-security-1000fib 550332648Receives traffic after security inspection

4.2 Why Two VRFs?

The split ensures a strict security boundary:

  • Pre-security VRF routes ALL matching prefixes toward the security service (frouter via Geneve). There is no direct route to the WAN/GRE — traffic must be inspected.
  • Post-security VRF routes inspected traffic back to the MPLS backbone (via GRE with appropriate label stacks). This VRF is only reachable after the security service returns the packet.
  • If both were in a single VRF, a routing misconfiguration could create a forwarding shortcut that bypasses the security service entirely.

4.4 VNI Bindings and VRF Mapping

The CNHE plugin uses VNI (Virtual Network Identifier) bindings to map Geneve tunnels to the correct VRF pair:

VNIHexSourcePurpose
10000x3E8Configured by datanode-agentStandard org VNI for agent-originated traffic
167772150xFFFFFFWire sentinel (cb->vni not set)MPLS-injected traffic: when packets enter via GRE/MPLS (not via Geneve), the CNHE buffer VNI field is unset. The midchain fixup writes 0xFFFFFF as the Geneve VNI.

Both VNIs map to the same VRF pair: pre-security table 16778216 and post-security table 50332648. When frouter reflects a Geneve packet with VNI=0xFFFFFF, CNHE matches the VNI binding and delivers the inner packet to org-post-security-1000.

The split VRF + Geneve VNI binding is what makes the security chain mandatory. MPLS disposition delivers to pre-security (which only has routes to frouter). Geneve return delivers to post-security (which only has routes to the backbone). There's no routing shortcut between them.

4.5 Additional VRFs on the Datanode

Besides the split org VRFs, the datanode has infrastructure VRFs:

VRFFIBTableRole
defaultfib 00Management, GRE outer IP (203.0.113.2). MPLS label 310 non-eos deags here.
LANfib 31LAN bridge (192.168.80.0/20). Carries Geneve underlay to frouter.
WANfib 42WAN bridge (192.168.48.0/20). Not used in this service chain.

The LAN VRF is critical: it carries the Geneve underlay traffic between the datanode's lan interface and the frouter. The CNHE midchain adjacency stacks: cnhe-gnv (Geneve header) → ip4 via 192.168.80.100 lan (underlay in LAN VRF). This ensures Geneve encapsulation uses the LAN bridge for underlay connectivity, completely separate from the org VRFs.

Datanode Setup Summary

This section documents every configuration change applied to the cnhe-datanode container to integrate it as a Security PE in the MPLS L3VPN topology. The setup is split across multiple scripts, executed in sequence.

Script execution order:

  1. setup-cnhe.sh — Base infrastructure: af-packet interfaces, MAC sync, interface detection
  2. IPsec tunnel must be established (creates org VRFs automatically)
  3. setup-cnhe-datanode-frouter.sh — Direct LAN approach (GRE branch), OR
  4. setup-cnhe-datanode-geneve.sh — CNHE Geneve approach (cnhe-integration branch)

Step 1: Base Infrastructure (setup-cnhe.sh)

af-packet Interface Creation

The datanode container has 10 network interfaces (eth0–eth9) connected to different Docker bridge networks. The script creates VPP af-packet host interfaces for each:

# Dynamically create af-packet interfaces for all ethX on cnhe-datanode
for iface in eth0 eth1 eth2 eth3 eth4 eth5 eth6 eth7 eth8 eth9; do
  vpp_exec cnhe-datanode "create host-interface name $iface"
  vpp_exec cnhe-datanode "set interface state host-$iface up"
done

MAC Address Synchronisation

VPP auto-generates 02:fe:* MACs for af-packet interfaces, but remote nodes (e.g., LSR2) ARP against the Linux veth MAC. Without syncing, VPP drops packets as "l3 mac mismatch". The script reads each Linux MAC and applies it to VPP:

# Sync VPP af-packet MACs with Linux MACs (eth0 through eth9)
for iface in eth0 eth1 eth2 eth3 eth4 eth5 eth6 eth7 eth8 eth9; do
  LINUX_MAC=$(docker exec cnhe-datanode cat /sys/class/net/$iface/address)
  vpp_exec cnhe-datanode "set interface mac address host-$iface $LINUX_MAC"
done

Interface-to-Network Detection

Docker assigns ethX interfaces in unpredictable order. The script detects which interface is on which subnet by checking Linux IP addresses:

# Detect datanode interface roles
DN_GRE=$(get_iface cnhe-datanode "203.0.113.")     # GRE transport (to LSR2)
DN_VRF10_IN=$(get_iface cnhe-datanode "100.64.100.") # VRF 10 ingress (to FW)
DN_VRF10_OUT=$(get_iface cnhe-datanode "100.64.101.") # VRF 10 egress (from FW)
DN_VRF20_IN=$(get_iface cnhe-datanode "100.64.102.") # VRF 20 ingress
DN_VRF20_OUT=$(get_iface cnhe-datanode "100.64.103.") # VRF 20 egress
DN_VRF30_IN=$(get_iface cnhe-datanode "100.64.104.") # VRF 30 ingress
DN_VRF30_OUT=$(get_iface cnhe-datanode "100.64.105.") # VRF 30 egress

Step 2: GRE Tunnel & MPLS (Both Approaches)

Both the frouter (direct LAN) and Geneve approaches share the same GRE tunnel and MPLS label setup on the datanode.

GRE Tunnel to LSR2

# GRE transport interface (toward LSR2 on 203.0.113.0/24)
set interface state host-eth9 up
set interface ip address host-eth9 203.0.113.2/24

# Sync MAC to prevent l3 mac mismatch drops
set interface mac address host-eth9 $DN_GRE_LINUX_MAC

# Create GRE tunnel (MPLS-over-GRE)
create gre tunnel src 203.0.113.2 dst 203.0.113.1
set interface state gre0 up
set interface ip address gre0 172.16.0.2/30

MPLS Label Processing

# Enable MPLS on GRE interface
mpls table add 0
set interface mpls gre0 enable

# Transport label: 310 non-eos → continue MPLS lookup for inner VPN label
mpls local-label 310 non-eos via mpls-lookup-in-table 0

# VPN label disposition: 1100 eos → IP lookup in org-pre-security VRF
mpls local-label 1100 eos via ip4-lookup-in-table $PRE_TABLE_ID

Label semantics: Transport label 310 is the outer label, popped first by the non-eos rule to expose the inner VPN label 1100. The eos rule on label 1100 sends the decapsulated IP packet to the org-pre-security VRF for inspection routing.

Step 3a: Direct LAN Approach (setup-cnhe-datanode-frouter.sh)

In this approach, pre-security traffic is forwarded to the frouter-simulator via the shared LAN bridge (192.168.80.0/24). The datanode, frouter, cortex, and broker are all on this network.

Pre-security Routes → Frouter VIP

# All VPN prefixes in pre-security VRF route to frouter VIP on LAN
FROUTER_VIP="192.168.80.100"
ip route add 10.1.1.0/24 table $PRE_TABLE_ID via $FROUTER_VIP lan
ip route add 10.1.2.0/24 table $PRE_TABLE_ID via $FROUTER_VIP lan
ip route add 100.64.1.0/24 table $PRE_TABLE_ID via $FROUTER_VIP lan
ip route add 100.64.5.0/24 table $PRE_TABLE_ID via $FROUTER_VIP lan
ip route add 10.100.1.0/24 table $PRE_TABLE_ID via $FROUTER_VIP lan

Post-security Routes → MPLS/GRE

# Inspected traffic exits via MPLS labels over GRE tunnel
# Toward PE1 (host1): transport 1400, VPN 600
ip route add 10.1.1.0/24  table $POST_TABLE_ID via 172.16.0.1 gre0 out-labels 1400 600
ip route add 100.64.1.0/24 table $POST_TABLE_ID via 172.16.0.1 gre0 out-labels 1400 600

# Toward PE2 (host2): transport 1500, VPN 500
ip route add 10.1.2.0/24  table $POST_TABLE_ID via 172.16.0.1 gre0 out-labels 1500 500
ip route add 100.64.5.0/24 table $POST_TABLE_ID via 172.16.0.1 gre0 out-labels 1500 500

Step 3b: Geneve Approach (setup-cnhe-datanode-geneve.sh)

In this approach, pre-security traffic is forwarded to the frouter-simulator via the CNHE Geneve tunnel (cnhe-gnv interface). This eliminates the three frouter bugs above because Geneve handles routing, MAC resolution, and VRF delivery natively.

CNHE Geneve Peer Discovery

# The cnhe-gnv interface is NBMA: routes use the peer UUID as an IPv6 next-hop
# Frouter IP 192.168.80.100 → UUID ff000000-...-c0a85064 → IPv6 ff00::c000:0:c0a8:5064
CNHE_PEER_IPV6=$(show cnhe peers cnhe-gnv | grep ff00::)

Pre-security Routes → Geneve Tunnel

# VPN prefixes in pre-security VRF route via CNHE Geneve to frouter
ip route add 10.1.1.0/24  table $PRE_TABLE_ID via $CNHE_PEER_IPV6 cnhe-gnv
ip route add 10.1.2.0/24  table $PRE_TABLE_ID via $CNHE_PEER_IPV6 cnhe-gnv
ip route add 100.64.1.0/24 table $PRE_TABLE_ID via $CNHE_PEER_IPV6 cnhe-gnv
ip route add 100.64.5.0/24 table $PRE_TABLE_ID via $CNHE_PEER_IPV6 cnhe-gnv
ip route add 10.100.1.0/24 table $PRE_TABLE_ID via $CNHE_PEER_IPV6 cnhe-gnv

VNI Binding for Geneve Return Path

When MPLS packets enter the datanode (not via Geneve), the CNHE buffer VNI is unset. The midchain fixup uses the sentinel value 0xFFFFFF (VNI 16777215) in the outgoing Geneve header. A VNI binding is needed so CNHE can match the tunnel on return and deliver the packet to the correct post-security VRF:

cnhe org add ip4 cnhe-gnv vni 16777215 \
  presec-table-ip4 $PRE_TABLE_ID \
  postsec-table-ip4 $POST_TABLE_ID

Post-security Routes (same as direct LAN)

# Same MPLS label stacks — the egress path is identical
ip route add 10.1.1.0/24  table $POST_TABLE_ID via 172.16.0.1 gre0 out-labels 1400 600
ip route add 10.1.2.0/24  table $POST_TABLE_ID via 172.16.0.1 gre0 out-labels 1500 500

Why Geneve is simpler: No frouter default gateway fix, no ICMP redirect suppression, no LAN VRF route leaks. Geneve decap uses the VNI binding to deliver packets directly to the org-post-security VRF, bypassing LAN VRF entirely.

Org VRF Tables (Created by IPsec Tunnel)

The org VRFs are not created by the setup scripts. They are created dynamically by the datanode when the IPsec tunnel is established. The table IDs are computed from the org ID and VNI:
